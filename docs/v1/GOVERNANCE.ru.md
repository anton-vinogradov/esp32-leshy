# ESP32-Leshy 1.x — документация как точка истины

*Читать на: [English](GOVERNANCE.md) · **Русский***

Статус документа: **обязательное правило проекта**.

Документация 1.x определяет продукт до реализации и подтверждает результат после
неё. Код, issue, устная договорённость или пункт меню 0.x не могут самостоятельно
изменить scope 1.x.

содержит живого статуса.

## Иерархия при конфликте

1. Безопасность, лицензии и законодательные ограничения.
2. Принятый requirement с идентификатором `PR-*` или `NFR-*`.
3. Каталог `CAP-*` как представление принятого scope без ослабления requirement.
4. Принятый ADR для конкретного технического решения.
5. Gate этапа `S*`, UX baseline и Stage Demo contract.
6. Архитектурное описание и исследования.
7. Реализация 1.x.

Конфликт не разрешается молча выбором документа «поновее». Работа останавливается на
затронутом участке, противоречие фиксируется в `STATUS`, затем нормативные документы
обновляются одним изменением. Код приводится к решению только после этого.

## Жизненный цикл изменения

Любое изменение поведения 1.x проходит один путь:

1. **Намерение:** указать пользовательскую задачу `J-*`, requirement `PR/NFR-*` и
   этап `S*`. Если их нет — сначала изменить документацию.
2. **Решение:** для значимого или трудно обратимого выбора принять ADR. Черновой ADR
   не разрешает реализацию как завершённую.
3. **Реализация:** код не выходит за критерии приёмки requirement и текущего этапа.
4. **Проверка:** добавить автоматическую либо HIL-проверку и сохранить ссылку или
   воспроизводимую команду как evidence.
5. **Синхронизация:** тем же изменением обновить traceability и текущий status.
6. **Gate review:** этап получает `done` только когда подтверждены все его exit
   criteria; процент готовности или «почти работает» gate не закрывает.

## Статусы

У этапа может быть один статус:

- `planned` — входные условия ещё не выполнены;
- `active` — текущий ограничитель проекта; одновременно только один;
- `blocked` — gate нельзя продвинуть без явно указанного внешнего условия;
- `done` — все результаты и evidence существуют;
- `reopened` — ранее закрытый gate нарушен новым фактом или регрессией.

Состояние требований: `draft`, `accepted`, `implemented`, `verified`, `deferred` или
`rejected`. `implemented` без evidence не равно `verified`.

## Нумерация прошивок

- Выпущенные artifacts `v0.*` остаются замороженной PoC-линейкой. Уже существующие
  внутренние checkpoints редизайна `0.1…0.207` сохраняются как неизменяемые
  идентификаторы evidence и никогда не переименовываются после сборки или прошивки
  их bytes.
- Следующая source-bearing сборка редизайна открывает публичное пространство 1.x как
  `1.0.0-dev.208`. Суффикс `dev.N` — монотонный инженерный checkpoint, а не
  пользовательский релиз.
- Phase-complete release candidates имеют вид `1.0.0-rc.N`. Первый публичный stable
  релиз редизайна — `1.0.0`; дальнейшие совместимые функции увеличивают minor, а
  совместимые исправления — patch.
- Версия идентифицирует точные неизменяемые bytes. Документация может объяснить или
  отклонить artifact, но не может переименовать его задним числом.

## Definition of Done

Работа считается завершённой, когда одновременно:

- существует requirement и измеримый критерий приёмки;
- реализация находится в чистой target 1.x и не создаёт зависимость от монолита 0.x;
- unit/integration/HIL-проверка соответствует риску;
- негативный сценарий, cancel/back и освобождение ресурсов проверены;
- EN/RU пользовательский текст и нормативные документы синхронизированы;
- traceability и `STATUS` обновлены;
- локальные ссылки, host tests и применимые firmware builds проходят.

## Правила поддержки документов

- `STATUS` обновляется при смене active stage, gate, blocker или подтверждённого
  результата; именно его дата считается датой актуальности проекта.
- Каждый переход фазы/checkpoint обновляет в `STATUS` поля snapshot `Текущая фаза`,
  `Проверенный checkpoint`, `Следующий evidence gate` и таблицу фаз active stage,
  после чего публичный roadmap README регенерируется командой
  `python3 tools/readme_roadmap.py --write`. `check_docs.py` отклоняет рассинхронизацию
  roadmap, состояний фаз и структуры EN/RU.
- `DELIVERY_PLAN` меняется только при изменении границ/порядка этапов, но не для
  ежедневного прогресса.
- Requirement не удаляется: он получает `rejected` или `deferred`, чтобы решения
  оставались объяснимыми.
- Значимый технический выбор не прячется в commit message: он получает ADR.
- Evidence не формулируется как «проверено вручную» без платы, процедуры, версии
  сборки и наблюдаемого результата.
- Переводы меняются вместе. При расхождении идентификатор и критерий приёмки считаются
  неопределёнными до исправления обеих версий.

## Минимальные поля ADR

```text
ADR-NNN: название
status: proposed | accepted | superseded | rejected
date:
requirements:
stage:
context:
decision:
alternatives:
consequences:
verification:
```

ADR нужен для формата хранения, resource/coexistence policy, framework/toolchain,
security boundary, публичного SDK/API и любого решения, замена которого потребует
миграции данных или переписывания нескольких слоёв.
